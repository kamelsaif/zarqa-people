# GoDaddy + Supabase cloud edition

الحزمة جاهزة للإعداد، لكنها لا تحتوي حسابات فعلية أو مفاتيح خدمات. إنشاء الملفات واجتياز الاختبارات لا يعني أن الموقع منشور أو أن البريد والمستندات متصلان. لا ترفع ملفات السيرفر أو مفاتيحه داخل مجلد الويب.

## Architecture

| Component | Responsibility | Where it runs |
|---|---|---|
| Static frontend | Arabic/English UI and Supabase sign-in | GoDaddy Apache/cPanel |
| Supabase Auth | Verified email/password sessions and recovery | Supabase |
| `hr-api` Edge Function | Authorization, business rules and integrations | Supabase Edge Functions |
| PostgreSQL | HR records, memberships, audit and delivery claims | Supabase |
| Google Drive | Restricted documents and encrypted snapshots | Company-controlled archive |
| Resend | Approved payslip notices linking to the private portal | Server-side API |

GoDaddy disk space holds frontend assets; it does not determine database, Drive or email quotas. The app does not require Node.js or PHP on GoDaddy. It is a single-company MVP using a versioned JSONB workspace and transactional writes, suitable for a small team; it is not a multi-tenant enterprise database.

## 1. Build the packages

Use Node.js 24 and Python 3 on a development machine:

```sh
npm ci
npm test
python3 scripts/package-cloud.py
```

`npm test` first builds the frontend and function bundle. Outputs:

- `artifacts/Zarqa-People-GoDaddy.zip`: static files including `.htaccess`; public config is blank and login remains locked.
- `artifacts/Zarqa-People-Cloud-Backend.zip`: bundled Edge Function, migration, owner bootstrap template and deployment guide.
- `artifacts/Zarqa-People-GitHub.zip`: sanitized source, tests, docs and CI workflow; no hosting identity or runtime keys.

The local demonstration in `dist/` intentionally retains fictional data and simulated roles. Upload only the GoDaddy artifact for real cloud use.

## 2. Initialize a dedicated Supabase project

1. Select/create the company's Supabase project. Record its project URL and publishable key privately in the deployment notes. Do not reuse another application's database without review.
2. In SQL Editor run `cloud/migrations/001_hr.sql`. All HR tables have RLS and no client-accessible policies. Do not grant browser table access to fix an app error.
3. In Authentication configure email/password access, disable open signup, require email verification and set Site URL to the intended HTTPS app origin. Add its exact root URL as an allowed redirect for recovery. Avoid wildcard redirect URLs.
4. Create/invite the owner in Supabase Auth. The owner completes verification and chooses their own password. If invite setup does not set a password, use the app's recovery flow after SMTP is configured.
5. Copy `cloud/bootstrap.example.sql` to an ignored local file and replace only `REPLACE_WITH_CONFIRMED_OWNER_EMAIL` with the verified owner's address. Run it once in SQL Editor. It refuses to replace an existing workspace or member list. Delete/store that configured copy privately afterward.

No default admin password or sample employee is created. First add company settings, employees and policies through the owner account. Then create/invite and verify users in Auth, and use **Data & accounts → Link registered user** to bind their verified email to the matching active employee profile. Manager/employee roles require a profile. Administrators can change roles or disable members in the app. The owner cannot be disabled or demoted there.

## 3. Set server secrets and deploy `hr-api`

Set secrets in the Supabase project's Edge Function settings. Never add their values to source control or the frontend:

| Variable | Value |
|---|---|
| `APP_ORIGIN` | Exact HTTPS origin, for example `https://hr.example.com`; no trailing slash or path |
| `SUPABASE_URL` | Project URL; provided by Supabase runtime |
| `SUPABASE_SERVICE_ROLE_KEY` | Server credential; provided by Supabase runtime |
| `SUPABASE_ANON_KEY` | Project anon key if available; provided by Supabase runtime |
| `RESEND_API_KEY` | Server-only email sending key |
| `EMAIL_FROM` | Address on a verified sending domain, e.g. `People <people@example.com>` |
| `GOOGLE_CLIENT_ID` | OAuth client ID for the company integration |
| `GOOGLE_CLIENT_SECRET` | OAuth client secret |
| `GOOGLE_REFRESH_TOKEN` | Offline refresh token authorized for the archive |
| `GOOGLE_DRIVE_FOLDER_ID` | Restricted archive root folder ID |
| `BACKUP_ENCRYPTION_KEY` | Cryptographically random 32-byte key encoded as 64 hex characters |

Use the official Supabase CLI or dashboard to deploy `cloud/supabase/functions/hr-api` **together with** `cloud/supabase/functions/_shared`. The latter is generated by `npm run build:cloud`. With the CLI authenticated and a project selected:

```sh
cd cloud
supabase link --project-ref YOUR_PROJECT_REF
supabase functions deploy hr-api --no-verify-jwt
```

`cloud/supabase/config.toml` also declares `verify_jwt = false`. This disables only the legacy gateway JWT check so newer signing keys work. The function itself calls Supabase Auth `/auth/v1/user` on **every request** and then checks the database membership. Do not remove those checks or expose the service-role key to callers. Anonymous POSTs must return 401.

## 4. Configure email and private documents

**Resend:** verify a sending domain using the exact DNS values shown in the account. Preserve existing MX/SPF/DKIM records; merge or add the instructed records, never replace unrelated email routing. Configure Supabase custom SMTP separately for Auth invitations and password recovery. Having a Resend API key for payroll notices does not configure Auth SMTP automatically. Verify recovery delivery with a test account before onboarding employees.

**Google Drive:** use a company-controlled OAuth integration with the Drive API enabled and offline access. Prefer the least scope that can access this application's dedicated archive. `drive.file` needs the archive to have been created/opened through that integration; do not assume it can access any pasted existing folder ID. If broader Drive access is required, review and authorize the exact scope with the owner. The account connected to ChatGPT does not automatically authorize this app.

Keep the archive's General access **Restricted**, check inherited permissions and do not share it with all employees. The backend mediates downloads. The connection check confirms read/write capability, not every sharing grant. Store the refresh token in server secrets only. OAuth consent/testing settings can affect token lifetime; validate the deployed integration rather than relying on an untested token.

Generate and store the backup key securely. Keep an independent recovery copy. The application does not generate or display this key to admins in the browser.

## 5. Upload the frontend to GoDaddy

1. Inspect the existing domain, DNS, website files and SSL before changing them. Take a private copy of files that would be replaced. If the root domain already serves a website, select a dedicated subdomain and document root instead of overwriting it.
2. Create/configure that domain in cPanel and verify HTTPS. The example hostname in this guide is not a deployment choice or a DNS instruction.
3. Extract `Zarqa-People-GoDaddy.zip` into its document root. Show hidden files and verify `.htaccess` was uploaded. Keep the ZIP and backend files outside the public document root.
4. Edit only `cloud-config.js` on the host:

```js
window.ZARQA_CONFIG = Object.freeze({
  supabaseUrl: 'https://YOUR_PROJECT_REF.supabase.co',
  publishableKey: 'YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY',
  functionName: 'hr-api'
});
```

The public key does not grant table access: the Auth session and server membership are required. Never insert an `sb_secret_` or service-role key here. Rebuilds restore the blank template, so reapply the public configuration deliberately when deploying a new artifact.

5. Verify HTTP redirects to HTTPS, the actual CSP and `Cache-Control` response headers, and no directory listing. If Apache returns 500, inspect the hosting error log and supported directives; do not remove security headers blindly.
6. Sign in as the confirmed owner, check the actual company name, configure policies and use Data & accounts to verify connected services.

## 6. Acceptance tests before real records

Use designated fictional test employees and mailboxes approved for testing:

1. An anonymous request and a confirmed Auth user without membership cannot read HR records.
2. An employee sees only their own profile/payslip. A manager cannot read another team's records or colleagues' compensation, including raw API responses.
3. Disable a test account; its existing session must lose access. Re-enable it and sign in again. Test password recovery and logout.
4. Open two sessions and save conflicting updates; the second must receive a refresh/review error without overwriting the first.
5. Upload a small PDF to an employee's document requirement. Verify the correct private folder, employee download, HR review and denied cross-employee download. Check sharing from Drive separately.
6. Prepare/review/approve a fictional payroll. Send one authorized test notice and verify actual delivery, portal access and print-to-PDF. A second send must not duplicate it. Each send handles at most 20 queued rows; use another explicit send for remaining rows.
7. Create an encrypted backup, download it privately and verify decryption with the held recovery key. Confirm the backup is not publicly accessible.

No live end-to-end pass is implied by the automated test suite. Record the date and deployment used when these checks pass.

## Recovery and operations

`hr_deliveries` is the durable email ledger. A notice accepted by Resend has a provider ID; `sending`/`review_required` requires investigation in Resend. Do not automatically clear or resend ambiguous claims. If saving a payroll snapshot conflicts after sending, refresh and send again to reconcile existing receipts without sending duplicates.

Backups are manual encrypted snapshots of workspace data and membership. They exclude original Drive documents, Auth credentials, the independent database audit table and the delivery ledger. Use provider/database backups for those resources too. Automatic email scheduling is disabled in this edition.

To decrypt an authorized downloaded snapshot on a private machine, make `BACKUP_ENCRYPTION_KEY` available through a secure local environment and run:

```sh
node scripts/decrypt-backup.mjs PRIVATE-DOWNLOAD.enc NEW-PRIVATE-OUTPUT.json
```

The utility refuses to overwrite an existing output file and writes private file permissions where supported. Never commit the output. For restoration, stop writes, back up the current database, review the decrypted snapshot, map membership IDs to the target project's verified Auth users, and preserve delivery/audit history. Restoration is deliberately not an automatic overwrite button.

Changing an employee's login email is not currently supported in-app: it requires coordinated Auth, membership and profile changes with a backup and identity re-verification. Social job ads, biometric devices, bank transfers, automatic taxes, statutory compliance and multi-company tenancy are outside this release.
